# 个人云功能需求

## 问题

Craft Hub 当前以本地优先方式运行，因此用户无法在多台电脑之间同步可移植的工作台信息，也无法在离开电脑时请求一台受信任的电脑运行已经发现的 capability。第一阶段云功能应验证这两类个人工作流，同时不得削弱 Craft Hub 的本地项目 trust 边界和结构化执行边界，也不得让公共 runtime 直接依赖 CloudBase。

## 范围

本规格覆盖一套实验性的第一方个人云集成，包括：

- 使用 YunLeFun 账号体系登录；
- 同步可移植的 workspace manifest 和全局设置；
- 注册和撤销桌面设备；
- 允许已认证用户为一个已发现的命令 capability 创建远程请求；
- 允许目标桌面端通过现有 Craft Hub runtime 领取、确认、执行并回报该请求；
- 将 CloudBase 作为首个托管实现，同时将厂商相关代码保留在核心领域模型之外。

第一版可以仅允许显式配置的 YunLeFun 用户白名单，并可以使用轮询代替持久 Relay 连接。

## 用户故事

### 1. 连接账号

作为 Craft Hub 云功能的首位用户，我希望通过系统浏览器连接 YunLeFun 账号，使 Craft Hub 无需获取或保存我的 YunLeFun 密码。

#### 验收标准

1.1. 当用户发起登录时，桌面应用必须在系统浏览器中打开配置的 YunLeFun 授权流程，并使用 PKCE、nonce、精确匹配的 redirect URI 和显式 scope 集合。

1.2. 当授权响应无效、过期、被重放、由其他环境签发，或者对应用户不在配置的白名单中时，个人云模块必须拒绝该响应，且不得创建本地会话。

1.3. 当登录成功时，桌面应用只能在操作系统安全存储中持久化应用专属的会话凭证，不得持久化 YunLeFun 密码、上游应用 session、CloudBase API key 或一次性 custom ticket。

1.4. 当用户退出登录或撤销设备时，个人云模块必须移除本地应用会话，并停止云同步和远程请求轮询。

### 2. 可移植数据云同步

作为用户，我希望同步可移植的 Craft Hub 信息，使另一台电脑可以恢复我的 workspace 组织结构，但不会同时获得本机权限或敏感信息。

#### 验收标准

2.1. 当同步模块上传本地状态时，只能包含带版本的 workspace manifest、workspace 排序，以及 runtime 已经归类为可移植的设置。

2.2. 当同步模块处理数据时，必须排除绝对路径、项目注册信息、本机绑定、trust 状态、凭证、环境变量、运行历史、终端输出、当前 UI 选择和外部 Agent task 标识。

2.3. 当远端与本地文档具有相同 revision 时，同步模块必须将该操作视为幂等操作。

2.4. 当本地和远端版本都相对于最后一个共同 revision 发生变化时，同步模块必须报告冲突并保留两个版本，不得静默覆盖任意一方。

2.5. 当同步得到的 workspace 引用了当前电脑上不存在的项目时，runtime 必须保持该成员为 unresolved，直到用户显式将其绑定到一个本地已注册项目；绑定操作不得转移 trust。

2.6. 当云端不可访问时，本地 runtime 必须保持可用，并在不阻塞本地项目发现和执行的前提下重试同步。

### 3. 设备注册

作为用户，我希望识别和撤销连接到账号的电脑，使远程请求只能发送到我控制的设备。

#### 验收标准

3.1. 当桌面端注册设备时，个人云模块必须在本地生成设备标识和设备密钥材料，并且只能上传公钥身份与非敏感设备元数据。

3.2. 当用户查看设备列表时，系统必须展示设备名称、平台、最后在线时间、可用状态和撤销状态，不得暴露本地路径或凭证。

3.3. 当设备被撤销时，云端必须拒绝使用该设备凭证认证的新请求领取和结果更新。

### 4. 异步远程 capability 请求

作为用户，我希望请求在线电脑运行一个已知 capability，使我可以远程启动安全的构建、测试或其他已声明的项目任务。

#### 验收标准

4.1. 当用户创建远程请求时，云端必须要求已认证账号、已注册的目标设备、可移植项目 key、命令 capability 标识、唯一 request ID 和过期时间。

4.2. 当桌面端收到请求时，必须将可移植项目 key 解析为本地已注册项目，并拒绝 unresolved、未知、非命令、已过期、重复或来自已撤销设备的请求。

4.3. 当解析得到的项目处于 untrusted 状态时，桌面端必须拒绝请求，且不得提供远程 trust 提升能力。

4.4. 在没有为精确匹配的设备、项目和 capability 显式开启远程自动批准时，当有效请求被领取后，桌面应用必须在执行前要求本地确认。

4.5. 当已批准请求开始执行时，桌面端必须复用现有的结构化命令 invocation、项目工作目录、`shell: false` executor、取消机制和运行记录行为。

4.6. 当请求投递或结果提交发生重试时，request ID 和领取租约必须确保命令最多执行一次。

4.7. 当请求执行状态变化时，桌面端必须发布有界状态记录，状态只允许为 `queued`、`claimed`、`awaiting_approval`、`running`、`succeeded`、`failed`、`rejected`、`cancelled` 或 `expired`。

4.8. 当请求结束时，第一版只能上传退出状态、退出码和时间戳；stdout、stderr、Codex 回复、完整运行历史与终端记录必须保留在本地。

### 5. 本地权威与可恢复性

作为用户，我希望云功能始终从属于本地 runtime，使云账号或云端服务失效时不会损坏或接管我的项目。

#### 验收标准

5.1. 当云端认证、同步或轮询失败时，本地 Craft Hub server 和桌面工作台必须继续运行。

5.2. 当云端请求尝试添加项目、修改路径、授予 trust、修改环境变量、运行原始 shell 文本或写入交互终端时，桌面端必须拒绝该请求。

5.3. 当个人云插件不存在或被禁用时，Craft Hub 必须保留当前本地行为和可移植文件格式。

5.4. 当厂商相关操作失败时，runtime 必须提供诊断信息，但不得泄露凭证、授权码、请求头、终端内容或环境变量。

## 约束

- 社区 runtime 必须保持厂商中立；CloudBase 集成由第一方个人云实现中的 Adapter 负责。
- 必须保留仓库中现有的未提交改动。
- 不得仅为预测假想 provider 而扩展公共 runtime 接口；实验性 seam 可以保留在内部，直到其行为得到验证。
- 现有 Codex Agent Task、结构化命令执行、运行记录、取消、终端和任务深链是唯一执行实现；个人云只能投递请求并调用这些现有能力，不得复制其状态模型或界面。
- CloudBase 环境 ID、端点、client ID 和允许登录的 subject 必须采用显式配置，不得硬编码生产密钥。
- CloudBase API key 和其他管理员凭证只能存在于服务端，绝不能打包进桌面端或 Web 客户端。
- 所有新增公共 runtime 接口必须使用严格 TypeScript，并提供 JSDoc。
- 涉及 runtime 行为的变更必须按适用范围补充 discovery、trust 和执行测试。

## 非目标

- 交互式远程终端附着或终端输入。
- 远程注册项目、选择路径、提升 trust、编辑环境变量或执行任意 shell。
- 公开注册、团队、组织、计费、订阅或通用多租户管理。
- 持续 WebSocket Relay、局域网点对点传输、推送通知或 Wake-on-LAN。
- 同步仓库、源文件、依赖、凭证、运行历史或 Agent 对话内容。
- 在云端重建 Codex 对话、Agent Task、终端、日志流、审批中心或通用远控界面。
- 在明确审查环境与安全配置之前部署生产 CloudBase 资源。
